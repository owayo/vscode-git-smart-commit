# 2026-11-20 定期点検

Reword が、一覧で選んだものとは別のコミットを書き換えることがあった。この不具合を含む 5 件を修正した。Git の呼び出しは非同期にし、拡張ホストのイベントループを止める時間を最長 316ms から 6ms に減らした。CI とリリースは、Node.js と pnpm の版を `mise.toml` から取る形に移した。テストは全 355 件が成功した。

## 修正した不具合

### Reword が別のコミットを書き換える

一覧で選んだコミットを、短縮ハッシュ (`git log` の `%h`) のまま `git-sc --reword` に渡していた。git-sc は対象を `git rev-parse --verify <値>^{commit}` で解決する。Git はこのとき、短縮ハッシュより同じ名前のタグやブランチを先に解決する。

実際の Git で再現した。コミット A の短縮ハッシュ `fff18cc` と同じ名前のタグをコミット B に付けると、`git rev-parse --verify fff18cc^{commit}` は B を返す。git-sc はそのまま B のメッセージを書き換える。

実行用の完全なハッシュ (`%H`) と表示用の短縮ハッシュ (`%h`) を、別々に取得するよう直した。一覧と進捗の表示は従来どおり短縮ハッシュを使う。

### `i18n.logOutputEncoding` で件名と作者名が文字化けする

`i18n.logOutputEncoding` を `Shift_JIS` などにした環境では、Git が件名と作者名をその文字コードで出力する。拡張は UTF-8 として読むので、Reword の一覧と確認画面の日本語が `���{��̌���` のように壊れていた。`git log` に `--encoding=UTF-8` を指定した。

### git-sc の起動の失敗が通知されない

起動の失敗の中には、`error` イベントではなく `spawn` の同期例外になるもの (EINVAL、Windows の EFTYPE など) がある。この例外はコマンドのハンドラで握りつぶされ、画面には何も出なかった。同期例外も `error` イベントと同じく通知してから、失敗として扱う。

EMFILE・ENFILE は別の形で壊れていた。Node.js は標準入出力を作らないまま `error` を発火する。拡張は先に `stdout.setEncoding()` を呼んで TypeError になり、`error` のリスナーを登録する前に止まっていた。結果として `error` イベントは未処理になり、停止時の後始末の対象にもプロセスが残った。終了イベントの登録を、標準入出力の設定より前に移した。

### エラーメッセージ中のパスで、エラーの種類を取り違える

Node.js のエラーメッセージには、実行したコマンドの行 (`git -C <フォルダー> ...` や実行ファイルのパス) が入る。拡張はメッセージ全体から文言を探していたため、パスに含まれる文言で判定が変わっていた。

- フォルダー名に `not a git repository` を含むと、所有権の拒否などの別のエラーを「Git 管理外」とみなした。SCM で対象を選ばずに実行すると、次の候補のリポジトリでステージとコミットが進む
- パスに `ENOENT` を含むと、Git や git-sc の別の失敗を「未導入」と表示した

「Git 管理外」は Git の診断の行頭 (`fatal: not a git repository`) だけを照合する。「未導入」はエラーコード (`ENOENT`) があればそれで判定し、Git の異常終了 (数値の終了コード) と区別する。

### pre-release のリリースが失敗する

リリースで pre-release を選んでも、VSIX は `--pre-release` なしで作っていた。vsce 4.1.0 は、印のない VSIX を `publish --packagePath --pre-release` で公開しようとすると拒否する。ovsx 1.4.0 は作成済みの VSIX に付けた `--pre-release` を無視し、安定版として公開する。VSIX の作成時に `--pre-release` を付けるよう直した。

## 性能: Git の呼び出しを非同期にした

`execFileSync` は、Git が終わるまで拡張ホストのイベントループを止める。このマシンでは Git を 1 回起動するたびに 20〜40ms かかった。Git 管理外のフォルダーが先頭に 10 個並ぶマルチルートでは、起動の回数だけ待ちが積み上がり、約 300ms 止まっていた。応答しないネットワークのファイルシステムでは、ほかの拡張の処理まで止まり続ける。

Git の呼び出し (`rev-parse`・`log`・`rev-list`) とフォルダーの `stat` を非同期にした。候補を先頭から 1 つずつ調べる順序と、エラーの分類は変えていない。`.git` を自前で探して Git の起動を省く案も検討したが、採らなかった。bare リポジトリ・`GIT_DIR`・`core.worktree`・`safe.directory` の扱いが Git と食い違い、本来は止まる候補を飛ばし得るためである。

変更前 (HEAD) と変更後の dist を交互に 60 回ずつ実行した中央値は次のとおり。環境は macOS arm64、Node.js 26.13.1、Git 2.56.1。「止めた時間」は、呼び出しから完了までの間に、1ms 間隔のタイマーの刻みが空いた最長の間隔である。同期の処理では完了までの時間と同じになる。

| 処理 | 完了まで (前 → 後) | 止めた時間 (前 → 後) |
| ---- | ----: | ----: |
| 履歴の取得 (100 件中 15 件) | 32.87 → 33.23ms | 32.87 → 3.29ms |
| 履歴の取得 (5 万件中 15 件) | 31.34 → 31.52ms | 31.34 → 3.09ms |
| ルートの検出 (1 フォルダー) | 25.47 → 26.40ms | 25.47 → 3.76ms |
| ルートの検出 (管理外 10 フォルダーの後) | 315.70 → 284.61ms | 315.70 → 6.00ms |
| PATH の解決 (同期のまま) | 0.42 → 0.44ms | 0.42 → 0.44ms |

完了までの時間は四分位範囲が重なり、変化はない。止めた時間は四分位範囲が重ならない水準まで下がった。残る 3〜6ms は、子プロセスの起動そのものなど同期で行われる部分である。[全測定値](command-preparation-2026-11-20.json)は次で再計測できる。

```bash
pnpm exec tsc -p ./ --outDir /tmp/after-dist
node scripts/benchmark-command-preparation.mjs --dist before=<変更前の dist> --dist after=/tmp/after-dist --runs 60
```

reword の `git log` の引数 (`%H` と `--encoding=UTF-8` の追加) も、hyperfine で比べた。5 万件の履歴で CPU 時間は 18.9ms と 17.9ms で、差はなかった。

準備中のキャンセルは入れていない。Git が応答しないとコマンドは終わらないが、拡張ホストは止まらなくなった。

## リファクタリング

Git ルートの検出と、検出に失敗したときの通知を `resolveCommandWorkspaceRoot.ts` にまとめた。`runGitSc.ts` と `rewordCommit.ts` に同じ 27 行があり、`runGitSc.ts` を変えた 17 回のコミットはすべて `rewordCommit.ts` も変えていた。2026-04-02 に ENOENT の通知を足したときも、2026-11-12 に SCM で選んだ対象を扱えるようにしたときも、2 か所に同じ修正が入っている。

`extension.ts` の commit 系の 4 コマンドは、コマンド ID と git-sc のオプションの表から登録する。2026-11-12 の修正では 5 つの登録すべてに同じ引数を足していた。

PATH の安全な要素だけを残すフィルターを `getSafePathDirectories` にまとめた。git-sc と git (`resolveExecutableOnPath` と `resolveNativeExecutableOnPath`) で同じ条件を 2 か所に書いていた。drive-relative のパスを除く修正も、両方に入れる必要があった。

`spawnGitScWithProgress` は 350 行の関数だが、分割しなかった。キャンセルの状態機械は前回の点検でも確認しており、変数を共有する閉包を分けると状態の受け渡しが増えるためである。

## CI とリリース

CI とリリースは `jdx/mise-action@v5` で Node.js と pnpm を入れる。`node-version` を 4 か所に書いていた二重管理をなくした。mise 本体は公開から 14 日以上たった版を使い、キャッシュは使わない。アクションは `actions/checkout@v7`・`upload-artifact@v7`・`download-artifact@v8` に上げた。

権限は最小にした。最上位は `contents: read` で、書き込みは版のコミットとタグを push するジョブと、GitHub Release を作るジョブだけが持つ。push しないジョブの checkout はトークンを残さない。

リリースは 4 つのジョブに分けた。

1. build: 依存を入れて VSIX を作る (読み取りのみ)。版は JST で採番する
2. tag: 依存を入れずに、同じ版を書いてコミットとタグを atomic に push する
3. publish: VS Marketplace と Open VSX へ公開する。トークンは `VSCE_PAT` と `OVSX_PAT` で渡す
4. github-release: GitHub Release を作る

依存の install スクリプトは、push できるトークンのあるジョブでは動かない。ビルドが成功してからタグを公開する順序は、前回の点検のまま保っている。本番のリリースは既定のブランチからだけ実行できる。dry run と既定のブランチ以外からの実行は別の同時実行グループに入れ、待機中の本番リリースを押し出さない。

`package.json` の `packageManager` は、mise を使わない開発者のために `mise.toml` と同じ版で残した。`pnpm-workspace.yaml` の `pmOnFail: error` により、版が食い違うと別の pnpm を黙って取得せずに失敗する。2 つの版の一致はテストで確かめる。

## 依存関係

`depup --install --include-pinned` は更新しなかった。公開から 14 日の条件を満たす候補は `@types/vscode` 1.145.0 だけだった。採用すると最低対応版も 1.145.0 に上がり、ローカルの VS Code 1.144.0 でインストールを確かめられないため、前回と同じく見送った。

depup は、既存の lockfile が 14 日の条件を満たさないとして止まった。前回 `--no-age` で取り込んだ版 (Biome 2.6.7 など) が、公開から 14 日たっていない。lockfile を作り直すと版が下がるので、作り直していない。

Biome 2.6.7 のために depup が加えた `minimumReleaseAgeExclude` は削除した。公開から 1 日以上たち、pnpm の既定の条件 (1 日) で除外が要らなくなった。lockfile は除外なしで pnpm の供給網の検査を通る。`biome migrate` の変更はなく、`pnpm audit --audit-level moderate` は 0 件だった。

## 指摘を受けて修正しなかったもの

codex (gpt-6.2-sol) のレビューで挙がった指摘のうち、次は確定の不具合として扱わなかった。

- 拡張ホストが `GIT_DIR`・`GIT_WORK_TREE` を引き継ぐと、SCM で選んだリポジトリより環境変数が優先される。Git の環境変数の仕様どおりの動きで、意図して設定する使い方もある
- UNC パスのリポジトリで `.cmd` 版の git-sc を使うと、cmd.exe が作業ディレクトリを Windows のディレクトリに替える。git-sc は失敗として報告され、別のリポジトリは操作しない
- キャンセル後、別のプロセスグループの子孫が標準出力を開いたままだと `close` が来ず、10 秒の上限が働かない。そうした子孫を起こす git-sc の経路を確認できていない
- `deactivate()` で出力チャンネルを破棄した後に、遅れて届いた出力の書き込みが例外になる。拡張ホストの終了処理の中でしか起きず、影響はログに限られる
- 準備中 (リポジトリの検出・履歴の取得) に拡張が停止しても、走っている Git は止めない。どれも読み取りだけで短時間に終わる。git-sc は、停止時に破棄した出力チャンネルを使う時点で例外になり、起動しない
- 履歴の取得が遅い間に別のリポジトリで reword を呼ぶと、先に呼んだ側の一覧が後から開くことがある。どちらの一覧も閉じれば何も変更しない
- POSIX の PATH 要素に、シンボリックリンクと `..` を組み合わせた値があると、探索先が OS の解決とずれる。発生条件が現実的でない
